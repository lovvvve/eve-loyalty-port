# 验证成员与管理端的核心操作界面

Type: prototype
Status: claimed
Parent: [规划 LP 转账信息管理平台](../map.md)
Blocked by: 05, 06, 07

## Question

制作一个低成本原型，让真实的成员、审核者、执行者与审计者走通“查看分发行方余额—申请或代建—审批—人工执行登记—对账确认—查询历史与异常”的完整闭环。哪些页面组织、状态表达、风险提示与操作反馈能让各角色正确理解当前责任，并减少错转、漏转和重复转？

### 2026-09-02 原型已建成，等待各角色走通后填写 Answer（检查点）

**分支选择**：按 `prototype` 技能判定为 **逻辑/状态模型原型**（LOGIC 分支），不是 UI 变体稿。理由：仓库尚无任何代码或路由框架；问题的核心是「03–08 号决策组成的闭环推到真实场景是否说得通、各角色是否知道下一步该谁做」。页面组织只做到「按角色分工作台 + 全局账本」这一层，视觉方向留待本票据解决后的信息架构工单。

**原型位置（随仓库提交保存，与 research/ 资产同样处理）**

- 首次提交于分支 `prototype/09-core-workflow`（已推送 origin），并入 main 后以 main 上的文件为准
- 文件：`.scratch/lp-transfer-platform/prototypes/09-core-workflow-prototype.html`，单文件、无依赖，双击即开，状态只在内存中
- 在线版本（私有 Artifact，可从页面分享给成员/审批者/执行者/审计者）：https://claude.ai/code/artifact/f5627d59-805b-4c45-b997-f747e25faf56
- 纯逻辑模块位于文件内 `@@MODULE-START` / `@@MODULE-END` 之间（`LoyaltyPortMachine`：`initialState` + `dispatch(state, action)`），不触碰 DOM，可整体搬入真实代码库作为状态机起点；页面壳可丢弃

**怎么用**：右栏选身份（阿雷/贝拉=成员，陈经办=财务，丁审批/癸审批=审批者，戊多职=审批+执行+复核，己执行=执行+复核，庚执行=执行，辛管理=管理员，壬审计=审计），左栏工作台只显示该身份可见内容；9 个引导场景从固定初始状态开始逐步点击（主路径、库存不足与 FIFO、重复提交与代建、领取超时、错转他人公司、越权与两人控制、超时取消与催办、期初异议、结算公司变更），每步标注「预期通过/被拦」；也可在「自由试玩」用任何身份点任何按钮，看拦截提示是否说清「为什么不行、该谁做」。

**已做的机械验证**：9 个场景共 117 步在 node 中逐步执行，实际通过/拦截结果与预期全部一致（0 处不符）；权益/预占/库存分配在完成、失败、撤回、取消、错转结案各路径下的联动均按 05/07 号决策落账。

**为写成状态机而做的简化假设 / 待确认设计点**（页面顶部可展开，走通后请逐条裁定是否写入规格）

1. 待库存 → 分配库存由系统在库存变化时自动按严格 FIFO 触发（05 号未写触发者；队头放不下则整体等待）。
2. 异常调查者由合格复核者自行「认领调查」（07 号只要求 24 小时内指派，未写由谁指派）。
3. 结构化登记与订单不一致或缺凭证时，系统硬性禁止复核者裁定「精确转出」——原型新增护栏。
4. 调查者裁定「精确转出/确认未转」直接生效；只有「确认错误事实并异常结案」生成账务处置提案走双审批。
5. 首次绑定结算公司若与期初提案登记的 `corporation_id` 不一致，也走 24 小时等待期（按 08 号推断，04 号对首次绑定未明确）。
6. 执行前 15 分钟余额确认简化为登记表单上的声明勾选，未勾选只记风险提示不阻断。
7. 「游戏操作后 30 分钟内提交登记」用领取独占到期这一个时钟代替。
8. 库存短缺只做负库存调整 + 原 FIFO 重算 + 建立库存差异案件；未模拟发行方级处理冻结、账外转账事件、LP 回收、维护模式、期初导入阶段关闭。
9. 疑似重复候选只在执行登记时提示，不做任何自动处置。
